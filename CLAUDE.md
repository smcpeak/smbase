## Overview

smbase is a general-purpose C++17 (plus some C99) utility library:
containers, strings, integers, exceptions/assertions, tracing, a test
framework, and GDValue/GDVN, a general data value type with a text
serialization format (see `gdvalue-design.txt`).  `index.html` is the
module catalog and the main documentation, grouped by function, with
obsolete modules marked.

It is typically employed as a git submodule of a client project that
lives in the parent directory and includes these headers as
`"smbase/..."`.  One example client is the `editor` project.

Primary development is on Windows under Cygwin and Linux.  On Windows,
the primary compilers are MinGW (winlibs) `g++` and `clang`; cygwin
compilation should ideally work but isn't regularly tested.  There may
be a `make-from-editor.sh` script that sets the PATH to various tools.

## Build and test

- `make`: builds `obj/libsmbase.a`, `obj/unit-tests.exe`, `obj/gdvn.exe`,
  and `obj/binary-stdin-test.exe`. All build outputs go in `$(OBJDIR)`
  (`obj/`), not next to the sources.
- `make check`: runs all tests. Parallel `-j` is fine. Test outputs and
  `.ok` stamp files go in `out/`, and `make check-clean` removes them.
- Settings go in `config.mk` / `personal.mk`; the variables are
  documented at the top of `Makefile` (for example, `WARNING_FLAGS = -Wall
  -Werror`, `OPTIMIZATION_FLAGS =`, `COVERAGE=1`, `ENABLE_MYPY=1`,
  `GENSRC=1`). `./configure` does nothing.
- `make compile_commands.json` combines the `obj/*.o.json` fragments.

### Unit tests

All unit tests link into one program, `obj/unit-tests.exe`.

- Run all of them: `obj/unit-tests.exe`
- Run one module's tests: `obj/unit-tests.exe <module>`, with
  underscores in place of hyphens (for example,
  `obj/unit-tests.exe ordered_flat_map`).
- Tests can read `VERBOSE=1` to print more. `UNIT_TESTS_TIMES=1` prints
  how long each test took.
- Assertions use the `sm-test.h` macros (`EXPECT_EQ`, `EXPECT_EXN_REGEX`,
  and so on).

To add a test module, start from `skeleton/module-test.cc`. Write
`foo-test.cc` defining a global `void test_foo()`, add `RUN_TEST(foo);`
to `unit-tests.cc` (which also declares the function), and add
`foo-test.o` to `UNIT_TEST_OBJS` in the `Makefile`. New library `.cc`
files go in `SRCS`. Both lists are kept in `LANG=C` sort order.

### Other checks run by `make check`

- **Expected-output tests.** `out/<mod>.unit.ok` (for example `gdvalue`,
  `boxprint`, `tree_print`) runs one unit test through
  `run-compare-expect.py` and compares with `test/<mod>.expect`. Inputs
  in `test/gdvn/*.gdvn` are run through `gdvn.exe` and compared with
  `*-expect`. To accept new output, rerun with `UPDATE_EXPECT=1`.
- **Compile-failure tests** (`check-compile-errs`). Some `*-test.cc`
  files contain `#if ERRNUM == n` blocks that must *not* compile, which
  is how the type-safety of `distinct-number`, `dni-vector`, `gdvalue`,
  and `sm-integer` is checked. They are registered with
  `EXPECT_COMPILE_TEST_FAIL` in the `Makefile`.
- **`check-coding-rules.py`** rejects CR characters in sources and
  top-level `using namespace` in headers.
- **`index.html`** is partly regenerated from each header's description
  line by `get-file-descriptions.py`. To add a new header, insert
  `<!-- new file descs: file1.h file2.h -->` in an appropriate section.
  Headers ending in `-fwd.h`, `-iface.h`, or `-ops.h` are excluded.
- **create-tuple-class.** Code between `// create-tuple-class:` markers
  (lines tagged `/*AUTO_CTC*/`) is generated by `create-tuple-class.py`.
  Don't edit it by hand. Edit the fields and rerun the script. The
  headers that use it are listed in `CTC_HEADERS` and checked with
  `--check`.
- The Python scripts have their own tests (`rce-tests`, `check-ctc`,
  `check-fts`, `test-ccr`) and are checked with `mypy --strict` when
  `ENABLE_MYPY=1`.

## Code conventions

- Files start with a `// filename` line and a one-line description (used
  by `index.html`), and end with `// EOF`. Each `#include` has a
  trailing comment naming what it provides.
- Includes of smbase headers use the `"smbase/..."` prefix (the build
  passes `-I..`). The module's own `-fwd.h` / `-iface.h` may be included
  without the prefix.
- Header guards are `SMBASE_<NAME>_H`.
- **Header split for larger (often template) modules:**
  - `foo-fwd.h` has forward declarations, for other headers to include
    in place of the full header.
  - `foo-iface.h` has the class declaration and documentation.
  - `foo-ops.h` (or, in some modules, `foo.h` itself) has the inline and
    template member definitions.
  - `foo.h` is what clients include to get the whole module.

  Prefer the `std-*-fwd.h` headers over full standard headers where a
  forward declaration is enough (`std-fwds.txt`).
- **Namespace.** Older code is in the global namespace. New code goes in
  `namespace smbase`, using `OPEN_NAMESPACE(smbase)` /
  `CLOSE_NAMESPACE(smbase)` and `OPEN_ANONYMOUS_NAMESPACE` from
  `sm-macros.h`. When an existing header is moved into the namespace,
  `SMBASE_GLOBAL_ALIAS` could add global `using` aliases for
  compatibility, but doing that is uncommon (`smbase-namespace.txt`).
- Assertions come from `xassert.h`: `xassert` (always on), `xassertdb`
  (debug only), and `xfailure`. Exceptions come from `exc.h`, and
  `stringb(...)` builds message strings.
- `sobjlist.h`, `objlist.h`, `strobjdict.h`, `strsobjdict.h`, and
  `strintdict.h` are generated by m4 from `xobjlist.h` /
  `xstrobjdict.h`, and are read-only. Edit the `x*.h` source and build
  with `GENSRC=1`.
- Most of the library is public domain (`license.txt`).
- Constructors and other special member functions use the DMEMB, etc.,
  macros defined in `sm-macros.h`.  See `dmemb-etc-macros.txt`.
- Namespaces are opened and closed using
  `{OPEN,CLOSE}[_ANONYMOUS]_NAMESPACE` macros defined in sm-macros.h,
  except in `-fwd.h` files, which use ordinary `namespace` open/close.
